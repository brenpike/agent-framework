## Implementation Steps

### STEP-001: fleet-dispatch Skill
**Owner:** coder
**File:** `plugin/skills/fleet-dispatch/SKILL.md` (new)

New pipeline skill that spawns N parallel orchestrator sessions. Behavior:

1. Receive fleet-plan from orchestrator (stream descriptions + branch names)
2. For each stream:
   a. Run `claude --worktree <branch_name> --tmux`
   b. Wait for tmux session ready
   c. Inject stream description via `tmux send-keys -t <session_name> "<description>" Enter`
3. Copy `.claude/settings.local.json` to each worktree's `.claude/` directory (if source exists)
4. Write fleet manifest to `.agent-framework/fleet/manifest.yaml`
5. Return manifest data to orchestrator (exit 0 with YAML on stdout)

Inputs:
- `streams`: array of `{name, description, branch}`
- `fleet_id`: ISO-8601 timestamp (generated by orchestrator)

Failure modes:
- tmux not installed → exit 1 with blocker
- `claude --worktree` fails → exit 1 with blocker
- Partial spawn (some succeed, some fail) → write manifest with failed streams marked, exit 1

Allowed tools: `Bash(claude *)`, `Bash(tmux *)`, `Bash(git worktree *)`, `Bash(cp *)`, `Bash(mkdir *)`, `Bash(printf *)`

### STEP-002: fleet-status Skill
**Owner:** coder
**File:** `plugin/skills/fleet-status/SKILL.md` (new)

User-invocable skill that reads the fleet manifest and reports status. Behavior:

1. Locate fleet manifest:
   a. If in main checkout: read `.agent-framework/fleet/manifest.yaml`
   b. If in worktree: resolve main checkout via `git worktree list | head -1`, read manifest from there
2. For each stream in manifest:
   a. Check tmux session alive: `tmux has-session -t <session_name>`
   b. Check branch exists: `git branch --list <branch>`
   c. Check PR state: `gh pr list --head <branch> --json number,state,mergeable`
   d. Update status based on external signals
3. Return formatted status table

This is an interactive skill (like plan-interrogation), not a pipeline skill. It produces user-visible output.

### STEP-003: Governance — workflow.md
**Owner:** coder
**File:** `plugin/governance/workflow.md`

Add section after "## Framework Defaults":

```markdown
## Fleet Execution

When the planner determines that work decomposes into multiple independent streams with minimal file-scope overlap, it may recommend `delivery: fleet`. The orchestrator confirms with the user before dispatching.

In fleet mode, the orchestrator enters coordinator mode:
1. Invokes `agent-framework:fleet-dispatch` to spawn child sessions
2. Monitors via `agent-framework:fleet-status` on demand
3. Reports aggregate status when all streams complete

Each child session is a standard orchestrator running a full pipeline. Children have no fleet awareness. The "one plan = one branch = one PR" invariant holds per child session.

Fleet-plan is a distinct artifact from plan artifact. Fleet-plans contain stream-level descriptions and scope boundaries. Plan artifacts contain implementation steps (STEP-NNN).

Version bumps, merge conflicts, and PR ordering are handled independently by each child, same as parallel developers on a team.
```

### STEP-004: Governance — definitions.md
**Owner:** coder
**File:** `plugin/governance/definitions.md`

Add after "## Validation Procedure":

```markdown
## Fleet

A set of parallel orchestrator sessions working on independent tasks in the same repository, each in its own git worktree. Spawned by the coordinator via `agent-framework:fleet-dispatch`.

## Coordinator Mode

The orchestrator execution mode entered when a fleet-plan is dispatched. The orchestrator remains on trunk in the main checkout, owns the fleet manifest, and serves as the status dashboard and on-demand helper for the fleet lifecycle. Coordinator mode responsibilities: dispatch, monitor, on-demand help, final report.

## Fleet-Plan

The planner's output artifact when work decomposes into multiple independent streams. Contains stream-level descriptions and scope boundaries, not step-level detail. Distinct from a plan artifact — fleet-plans do not contain STEP-NNN entries.

## Stream

One independent unit of work within a fleet-plan, assigned to a single child orchestrator session. Each stream has its own worktree, branch, pipeline execution, and PR.
```

## Delivery Shape

Single PR. All steps are tightly coupled (new skills + governance + orchestrator awareness). Splitting into multiple PRs creates intermediate states where governance references nonexistent skills or vice versa.

Note: The original 12-step plan was reduced to 7 steps during interrogation. Four skill-modification steps (create-working-branch, checkpoint-commit, open-plan-pr, fix-ledger) were eliminated because children have no fleet awareness and worktrees handle state isolation automatically.

## Risks

| Risk | Mitigation |
|---|---|
| `claude --worktree` behavior changes | Fleet-dispatch can fall back to manual `git worktree add` + `claude --tmux` |
| Poor planner decomposition → merge conflicts | Planner quality signal; user can reject fleet-plan and execute sequentially |
| N sessions × token cost | User confirms fleet deployment; no hidden parallelism |
| tmux send-keys timing | Fleet-dispatch waits for session ready signal before injecting task |
| Orphaned worktrees from crashed sessions | Claude Code built-in cleanup; `git worktree prune` as manual fallback |
